# DiscFlow 分布式刻录系统设计

## 1. 目标与约束

核心约束是**一台刻录机同一时刻只能执行一个刻录任务**。系统的并发入口和串行执行必须分离：Web/API 可以同时接收多个请求，物理刻录只能由一个消费者顺序执行。

当前版本覆盖一个刻录站点的最小可用闭环：

- 局域网电脑通过浏览器选择文件、文件夹或上传 ISO。
- NestJS 接收请求、保存源文件、持久化任务并实时推送状态。
- Windows 刻录服务器调用 IMAPI2 生成光盘镜像并把数据写入刻录机。
- 浏览器可以查询排队位置、上传/刻录状态、失败原因，并重试或取消未开始的任务。

## 2. 部署拓扑

```text
┌────────────────────┐       HTTP / SSE        ┌────────────────────────────┐
│ Windows 客户端电脑  │ ──────────────────────> │ Windows 刻录服务器          │
│ React Web 页面      │ <────────────────────── │ NestJS API + 串行任务队列   │
└────────────────────┘                         │ 本地磁盘 + IMAPI2 代理      │
                                               └─────────────┬──────────────┘
                                                             │ COM
                                                       ┌─────▼─────┐
                                                       │ 刻录机     │
                                                       └───────────┘
```

客户端不需要安装专用软件，也不需要直接访问刻录机。文件先上传到刻录服务器，因此刻录期间客户端可以离线；任务状态以服务器为准。

## 3. 模块职责

| 模块 | 职责 |
| --- | --- |
| Job API | multipart 上传、参数校验、任务查询、取消和重试 |
| Staging | 将上传文件移入任务目录，保留文件夹相对路径，限制路径穿越 |
| Queue | 使用先进先出内存队列，只启动一个消费者 |
| Snapshot Store | 以原子写入方式持久化任务元数据，支持进程重启恢复 |
| IMAPI2 Runner | 把任务清单交给 Windows PowerShell 代理，解析进度和错误 |
| SSE Gateway | 向所有浏览器广播任务快照，不要求客户端轮询 |
| React Client | 选择文件/ISO、上传进度、队列与刻录状态展示 |

选择内存队列加本地快照，是因为单刻录站点没有横向消费需求。队列的持久语义由状态机和服务启动恢复逻辑提供，不引入 Redis，从而减少部署组件。升级到多个刻录站点时再替换为持久消息队列。

## 4. 任务状态机

```text
queued ──> preparing ──> burning ──> completed
  │             │            │
  ├──> cancelled│            └──> failed
  │             └──> failed
  └──────────────> queued (服务恢复)

failed / cancelled ──> queued (显式重试)
```

关键规则：

1. 只有 `queued` 可以取消；已经交给刻录机的任务不能假装取消成功。
2. 进程异常退出时，`preparing`/`burning` 标记为失败，不自动重烧。
3. 重试保留原始上传文件，并追加到队列尾部，避免插队。
4. 成功刻录后默认清理源文件；可配置为保留用于审计。

## 5. HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/jobs` | 返回所有任务、队列长度和刻录机状态 |
| `POST` | `/api/jobs` | 上传文件或 ISO 并创建任务 |
| `GET` | `/api/jobs/:id` | 查询单个任务 |
| `POST` | `/api/jobs/:id/cancel` | 取消仍在排队的任务 |
| `POST` | `/api/jobs/:id/retry` | 将失败任务重新加入队尾 |
| `GET` | `/api/events` | SSE 实时快照流 |
| `GET` | `/api/health` | 服务健康检查 |

创建任务使用 `multipart/form-data`：

| 字段 | 说明 |
| --- | --- |
| `mode` | `files` 或 `iso` |
| `discName` | 光盘卷标，最长 64 个字符 |
| `relativePaths` | 与文件顺序一致的 JSON 字符串数组，用于保留文件夹结构 |
| `files` | 一个或多个文件；ISO 模式必须恰好一个 `.iso` 文件 |

## 6. IMAPI2 执行边界

NestJS 不直接加载 COM。它只生成任务清单并启动有超时和错误捕获的 PowerShell 子进程。这样可以：

- 将 Node.js 的事件循环与同步 COM 刻录过程隔离。
- 让刻录代理单独升级、单独测试，并在失败时释放进程资源。
- 未来把本机代理替换为另一台机器上的 Burn Agent，而不修改 Web API。

代理先从 `IMAPI2.MsftDiscMaster2` 枚举刻录机，再创建 `IMAPI2.MsftDiscFormat2Data` 写入盘片。文件模式同时使用 `IMAPI2FS.MsftFileSystemImage` 创建 ISO9660/Joliet 镜像流，不依赖额外光盘映像工具。

## 7. 多刻录站点扩展

当一台服务器需要管理多台刻录机时，按以下边界拆分：

1. **Coordinator API**：只接收任务并写入 PostgreSQL。
2. **Burn Agent**：每个刻录机一个消费者，向协调器注册 `stationId`、能力和在线状态。
3. **任务队列**：使用 BullMQ/Redis 或云消息队列，队列键包含 `stationId`，保证同一刻录机串行。
4. **租约与心跳**：Agent 领取任务后写入租约；心跳丢失后任务进入人工核查，而不是自动重烧。
5. **对象存储**：大 ISO 不再存放在 API 本地磁盘，改用共享存储或预签名上传。
6. **认证与审计**：加入用户登录、权限、任务操作日志和光盘序列号记录。

任务模型已经与执行器分离，升级时主要替换 Queue 和 Runner 两个模块。

## 8. 容量、安全与运维

- 默认单请求上限 8 GiB，可通过 `MAX_UPLOAD_BYTES` 调整。
- 文件名会去除目录穿越片段，目标路径被限制在任务目录内。
- 局域网部署只开放专用网段；跨网段使用反向代理、HTTPS 和认证。
- 监控至少包括磁盘剩余空间、上传失败率、队列等待时间、刻录时长和失败率。
- 盘片、刻录机、IMAPI2 驱动属于物理环境变量，生产上线前必须用真实硬件做端到端验收。
